# Init Containers in Kubernetes

## Overview

An **Init Container** is a specialized container in a Kubernetes Pod that runs **before the main application containers start**.

Init containers are useful when an application needs some setup or initialization to be completed before the main application can run. They can perform tasks such as configuration generation, dependency checks, file creation, or data initialization.

The main application containers start only after all init containers have completed successfully.

---

## What Are Init Containers?

Init containers are specialized containers that execute initialization tasks before the main application containers in a Pod are started.

The execution flow is:

```text
Pod Starts
    |
    v
Init Container
    |
    |-- Initialization / Setup
    |
    v
Init Container Completes
    |
    v
Main Application Container Starts
```

If there are multiple init containers, they run sequentially. The next init container starts only after the previous one completes successfully.

Only after all init containers have completed successfully does Kubernetes start the main application containers.

This provides a predictable and prepared environment for the application.

---

## Key Characteristics

### 1. Sequential Execution

Init containers run sequentially.

One init container must complete successfully before the next init container starts.

The main application container does not start until all init containers have finished.

### 2. Restart Behavior

If an init container fails, the Kubernetes kubelet automatically restarts it until it succeeds.

However, if the Pod's restart policy is set to `Never`, a failing init container causes the entire Pod to fail and stops further execution.

### 3. Temporary and Disposable

Init containers are transient.

Once an init container completes, it is terminated. Only its results remain available to the main application containers.

For example, an init container can create files or prepare data in a shared volume that the main container later uses.

### 4. Different Runtime Environment

An init container can use a different image from the main application container.

This allows setup utilities or tools to be included only in the initialization step without adding them to the main application image.

# Lab Objective

In this lab, an init container is used to prepare content for an NGINX web server.

The lab will:

- Create a Pod named `my-pod`
- Run an NGINX container as the main application container
- Add an init container named `my-init`
- Use the BusyBox image for the init container
- Create an HTML file containing `hello world`
- Use a shared `emptyDir` volume between the containers
- Verify that NGINX serves the content generated by the init container

---

# Architecture

The Pod contains two containers:

```text
                    my-pod
                      |
          +-----------+-----------+
          |                       |
          v                       v
     my-init                   nginx
    BusyBox                    NGINX
       |                         |
       | creates                 | serves
       | index.html              |
       v                         v
       +-------- shared ---------+
                emptyDir
```

The init container creates the HTML file in the shared volume.

The NGINX container mounts the same volume at:

```text
/usr/share/nginx/html
```

As a result, NGINX can serve the file created by the init container.

---

# Step 1: Create the Pod Definition

Create a YAML file:

```bash
vim pod.yaml
```

Add the following configuration:

```yaml
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: null
  labels:
    run: my-pod
  name: my-pod
spec:
  containers:
  - image: nginx
    name: nginx
    resources: {}
    volumeMounts:
    - name: demo
      mountPath: /usr/share/nginx/html

  initContainers:
  - name: my-init
    image: busybox:1.28
    command: ['sh', '-c', 'echo "hello world" > /tmp/index.html']
    volumeMounts:
    - name: demo
      mountPath: "/tmp/"

  dnsPolicy: ClusterFirst

  volumes:
  - name: demo
    emptyDir: {}

  restartPolicy: Always

status: {}
```

---

# Step 2: Understand the Pod Configuration

## Main Container

The main application container uses:

```yaml
- image: nginx
  name: nginx
```

It mounts the shared volume at:

```text
/usr/share/nginx/html
```

This is the directory from which NGINX serves the web content.

---

## Init Container

The init container is:

```yaml
initContainers:
- name: my-init
  image: busybox:1.28
```

It executes:

```bash
sh -c 'echo "hello world" > /tmp/index.html'
```

This creates:

```text
/tmp/index.html
```

inside the init container.

The `/tmp/` directory is backed by the shared `emptyDir` volume.

---

## Shared Volume

The Pod defines:

```yaml
volumes:
- name: demo
  emptyDir: {}
```

Both containers mount this same volume.

### Init Container

```yaml
volumeMounts:
- name: demo
  mountPath: "/tmp/"
```

### NGINX Container

```yaml
volumeMounts:
- name: demo
  mountPath: /usr/share/nginx/html
```

Therefore, the file created by the init container becomes available to NGINX through the shared volume.

---

# Step 3: Apply the Pod Configuration

Create the Pod:

```bash
kubectl apply -f pod.yaml
```

Verify the Pod:

```bash
kubectl get pods
```

During startup, the Pod may go through states such as:

```text
Init:0/1
Init:1/1
Running
```

This indicates that the init container is completing its initialization before the main NGINX container starts.

---

# Step 4: Verify the Init Container Execution

Once the Pod reaches the `Running` state, access the Pod:

```bash
kubectl exec -it my-pod -- sh
```

Inside the Pod, test the NGINX response:

```bash
curl localhost
```

Expected output:

```text
hello world
```

This confirms that:

1. The init container successfully created the HTML file.
2. The file was placed in the shared volume.
3. NGINX accessed the same shared volume.
4. NGINX successfully served the generated content.

---

# Step 5: Additional Verification

The Pod description can be inspected with:

```bash
kubectl describe pod my-pod
```

This provides details about the Pod lifecycle and container execution.

To inspect the init container logs:

```bash
kubectl logs my-pod -c my-init
```

These commands can help understand the initialization and Pod execution flow.

# Execution Flow

The complete execution sequence can be summarized as:

```text
1. Kubernetes creates the Pod
            |
            v
2. my-init starts
            |
            v
3. BusyBox creates /tmp/index.html
            |
            v
4. my-init completes successfully
            |
            v
5. NGINX container starts
            |
            v
6. NGINX reads the shared volume
            |
            v
7. curl localhost
            |
            v
8. "hello world"
```

# Key Takeaways

- Init containers run before the main application containers.
- Init containers execute sequentially.
- The main application starts only after all init containers complete successfully.
- A failed init container can be restarted by the kubelet until it succeeds.
- Init containers are temporary and terminate after completing their task.
- Init containers can use a different image from the main application.
- A shared `emptyDir` volume can be used to pass generated files or prepared data from an init container to the main container.
- In this lab, BusyBox prepares the HTML content and NGINX serves it.
